# RAG 기반 음악 큐레이션 요구사항 정의서

<!-- markdownlint-disable MD013 -->

## 1. 개요 및 배경

기존의 AI 플레이리스트 큐레이션 흐름은 사용자의 자연어 프롬프트에만 의존하여
LLM이 자체 지식으로 음악 후보를 추천하는 방식이었습니다. 이 방식은 LLM이
실제 존재하지 않는 가짜 곡을 지어내거나(환각 현상), 스포티파이 카탈로그에
부합하지 않는 트랙을 반환해 최종 플레이리스트 저장이 실패하는 문제점이
있었습니다.

본 요구사항 정의서는 스포티파이 카탈로그 지식을 사전 검색(Retrieval)하여
LLM에 컨텍스트로 제공하고, 이를 기반으로 분위기에 부합하는 실존 음원을 정교하게
큐레이션하는 **RAG(Retrieval-Augmented Generation) 기반 음악 추천 시스템**의
요구사항을 기술합니다.

---

## 2. 기능적 요구사항 (Functional Requirements)

### FR-1: 1차 추천 검색 쿼리 추출 및 추천 후보군 조회

* **FR-1.1**: 사용자의 자연어 감정/분위기 프롬프트를 입력받으면, 1차로
  초경량 LLM을 호출하여 프롬프트 무드에 가장 잘 어울리는 스포티파이 검색 쿼리
  (장르 필터 혹은 대표 아티스트 키워드) **최대 3~5개**를 추출해야 한다.
* **FR-1.2**: 추출된 검색 쿼리들로 스포티파이 Search API(`GET /v1/search?q=...&type=track&limit=10`)를
  병렬 호출하여, 실제 플랫폼에 존재하는 **30~50곡의 1차 추천 후보군**을 획득해야 한다.

### FR-2: 후보군 메타데이터 컨텍스트 구성

* **FR-2.1**: 스포티파이 Recommendations/Audio Features API의 지원 중단(Deprecated)에
  대응하여, 1차로 획득한 추천 후보군의 트랙 정보(곡명, 아티스트명, 트랙 ID/URI)를 2차 최종 LLM
  컨텍스트로 전달해야 한다.
* **FR-2.2**: 별도의 외부 오디오 피처 조회 없이, LLM 자체의 음악적 배경 지식을 활용해
  각 후보 트랙의 감성/무드를 매핑하도록 시스템을 설계한다.

### FR-3: 분위기 가중 RAG 최종 큐레이션 및 선별

* **FR-3.1**: 수집된 30~50곡의 실존 음원 후보군 텍스트와 원래의 분위기 프롬프트를
  2차 최종 LLM의 컨텍스트로 전달해야 한다.
* **FR-3.2**: 최종 LLM은 사용자가 입력한 분위기 프롬프트와의 매칭을 최우선으로 적용하여,
  자체 지식을 바탕으로 후보군 중 가장 극적인 조화를 이루는 **10~15곡**을 최종 선별해야 한다.
* **FR-3.3**: 최종 선별된 각 곡이 왜 이 분위기에 어울리는지에 대한
  음악적/감성적 큐레이션 사유(`playlistDescription` 및 각 트랙 코멘트)를
  사용자에게 제공해야 한다.

### FR-4: API 실패 대응 폴백(Fallback) 처리

* **FR-4.1**: 스포티파이 검색 API 조회 결과가 없거나 API 호출 실패(레이트
  리밋, 인증 오류 등)가 발생하면, 사용자의 기존 **최근 재생 곡 목록**을
  큐레이션 후보군이자 최종 플레이리스트의 골격으로 그대로 반환(Option A)하여
  무중단 서비스를 보장해야 한다.

## 3. 비기능적 요구사항 (Non-Functional Requirements)

### NFR-1: 성능 및 응답 속도 (Latency)

* **NFR-1.1**: 1차 검색어 추출 LLM 호출, Search API 병렬 조회, 2차 최종 필터링 LLM 호출 등
  다단계 네트워크 통신이 수반되므로, 각 구간별 비동기 병렬 처리 및 최적화를 적용해야 한다.
* **NFR-1.2**: 전체 큐레이션 API 호출의 최대 타임아웃은 **25초**로 제한하며,
  구간별 타임아웃 제어(예: LLM 호출당 10초)를 통해 오류 전파를 차단해야 한다.

### NFR-2: 데이터 정합성 및 안전성

* **NFR-2.1**: 최종 반환된 10~15곡은 반드시 실존하는 스포티파이
  트랙 URI(`spotify:track:xxxx`)를 보유하고 있어야 하며, 가짜 데이터의
  유입을 원천적으로 차단해야 한다.
* **NFR-2.2**: API 응답 중 민감한 개인 세션 토큰 등은 백엔드 내부에서만
  소비되고 외부 콘솔이나 사용자 인터페이스에 노출되지 않도록 마스킹 처리한다.
