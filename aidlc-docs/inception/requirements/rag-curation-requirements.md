# RAG 기반 음악 큐레이션 요구사항 정의서

<!-- markdownlint-disable MD013 -->

## 1. 개요 및 배경

기존의 AI 플레이리스트 큐레이션 흐름은 사용자의 자연어 프롬프트에만 의존하여
LLM이 자체 지식으로 음악 후보를 추천하는 방식이었습니다. 이 방식은 LLM이
실제 존재하지 않는 가짜 곡을 지어내거나(환각 현상), 스포티파이 카탈로그에
부합하지 않는 트랙을 반환해 최종 플레이리스트 저장이 실패하는 문제점이
있었습니다.

본 요구사항 정의서는 스포티파이 카탈로그 지식을 사전 검색(Retrieval)하여
LLM에 컨텍스트로 제공하고, 이를 기반으로 분위기에 부합하는 실존 음원을 정교하게
큐레이션하는 **RAG(Retrieval-Augmented Generation) 기반 음악 추천 시스템**의
요구사항을 기술합니다.

## 2. 기능적 요구사항 (Functional Requirements)

### FR-1: 사용자 프롬프트의 3축 SPEC 분해

* **FR-1.1**: 사용자의 자연어 프롬프트를 입력받으면, LLM은 즉시 검색어만
  만들지 않고 먼저 다음 세 가지 SPEC으로 의도를 분해해야 한다.
  * **장르/감성 SPEC**: 듣고 싶은 장르, 무드, 템포, 에너지, 시대감,
    밝기/어두움, 보컬/연주곡 성향 등 음악적 감각을 구조화한다.
  * **장소/청취 맥락 SPEC**: 드라이브, 카페, 운동, 새벽 작업, 파티,
    산책, 여행, 집중, 휴식처럼 음악이 울릴 공간과 활동 맥락을 구조화한다.
  * **아티스트/곡 SPEC**: 사용자가 언급한 아티스트, 비슷한 아티스트,
    특정 곡 제목, 참고 곡, 피해야 할 아티스트/곡이 있으면 분리해 기록한다.
* **FR-1.2**: 각 SPEC은 `confidence`, `mustHave`, `niceToHave`, `avoid`
  성격을 함께 가져야 하며, 사용자가 명시하지 않은 값은 LLM이 추론하되
  추론값임을 표시해야 한다.
* **FR-1.3**: 프롬프트가 짧거나 모호해도 기본 API 흐름은 중단하지 않고
  내부 추론으로 SPEC을 채운다. 단, 향후 대화형 UX를 도입할 경우 같은
  SPEC 구조를 사용자 확인 질문의 기반으로 재사용할 수 있어야 한다.

### FR-2: SPEC 기반 내부 멀티턴 검색 계획 수립

* **FR-2.1**: LLM은 세 가지 SPEC을 바탕으로 한 번에 하나의 검색어 목록만
  반환하지 않고, 내부 멀티턴 검색 계획을 생성해야 한다.
* **FR-2.2**: 검색 계획은 최소 다음 라운드를 포함해야 한다.
  * **Round A - Genre/Mood Retrieval**: 장르/감성 SPEC에 맞는 장르,
    무드 키워드, 대표 아티스트 기반 검색 쿼리를 생성한다.
  * **Round B - Place/Context Retrieval**: 장소/활동 맥락에 어울리는
    키워드와 플레이리스트형 표현을 검색 쿼리로 확장한다.
  * **Round C - Artist/Title Retrieval**: 명시된 아티스트와 곡, 그리고
    유사 아티스트 후보를 중심으로 검색 쿼리를 생성한다.
  * **Round D - Artist Depth Expansion**: 최종 후보에 포함될 가능성이
    높은 아티스트마다 최소 3곡 확보를 목표로 추가 검색한다.
* **FR-2.3**: 각 라운드는 Spotify Search API(`GET /v1/search?q=...&type=track`)를
  사용할 수 있는 쿼리 목록, 기대 후보 수, 중복 제거 기준, 실패 시 다음
  라운드로 넘어가는 조건을 명시해야 한다.

### FR-3: 후보군 메타데이터 컨텍스트 구성 및 확장

* **FR-3.1**: 스포티파이 Recommendations/Audio Features API의 지원 중단(Deprecated)에
  대응하여, 검색으로 획득한 후보군의 트랙 정보(곡명, 아티스트명, 트랙 ID/URI)를
  최종 LLM 컨텍스트로 전달해야 한다.
* **FR-3.2**: 후보군은 라운드별 결과를 병합하되 Spotify `id` 또는 `uri`
  기준으로 중복 제거해야 한다.
* **FR-3.3**: 2~3시간 길이의 플레이리스트 생성을 허용하기 위해, 후보군은
  기존 30~50곡보다 넓게 수집할 수 있어야 한다. 기본 목표는 80~150곡
  후보군이며, API 실패 또는 결과 부족 시 가능한 범위까지 축소한다.
* **FR-3.4**: 별도의 외부 오디오 피처 조회 없이, LLM 자체의 음악적 배경
  지식을 활용해 각 후보 트랙의 감성/장소/아티스트 적합도를 매핑하도록
  시스템을 설계한다.

### FR-4: 긴 플레이리스트 및 아티스트별 깊이 규칙

* **FR-4.1**: 최종 LLM은 사용자가 입력한 분위기 프롬프트와의 매칭을 최우선으로
  적용하여, 후보군 중 가장 조화로운 트랙을 선별해야 한다.
* **FR-4.2**: 최종 선별 목표는 짧은 MVP 기본값 10~15곡으로 제한하지 않는다.
  사용자가 별도 곡 수를 지정하지 않아도 2~3시간 플레이리스트가 될 수
  있도록 약 30~50곡 수준의 최종 결과를 허용한다.
* **FR-4.3**: 최종 결과에서 동일 아티스트가 포함될 경우, 가능한 한 해당
  아티스트당 최소 3곡을 확보한다.
* **FR-4.4**: Spotify Search 결과상 특정 아티스트의 곡이 3곡 미만이거나,
  중복/부적합 곡만 반환되는 경우에는 1~2곡만 포함할 수 있다. 이 경우
  시스템은 부족 사유를 내부 메타데이터 또는 큐레이션 설명에 반영해야 한다.
* **FR-4.5**: 최종 선별된 각 곡 또는 아티스트 그룹이 왜 이 분위기와
  장소 맥락에 어울리는지에 대한 음악적/감성적 큐레이션 사유를
  `playlistDescription` 및 트랙/그룹 코멘트로 제공해야 한다.

### FR-5: API 실패 대응 폴백(Fallback) 처리

* **FR-5.1**: 스포티파이 검색 API 조회 결과가 없거나 API 호출 실패(레이트
  리밋, 인증 오류 등)가 발생하면, 사용자의 기존 **최근 재생 곡 목록**을
  큐레이션 후보군이자 최종 플레이리스트의 골격으로 그대로 반환(Option A)하여
  무중단 서비스를 보장해야 한다.
* **FR-5.2**: 특정 라운드만 실패한 경우 전체 큐레이션을 즉시 중단하지 않고,
  성공한 라운드의 후보군으로 최종 선별을 계속 진행해야 한다.

### FR-6: 생성 후 검증 및 자동 수리

* **FR-6.1**: 최종 LLM이 플레이리스트를 생성한 뒤, 시스템은 결과를 즉시
  사용자에게 반환하거나 Spotify에 저장하지 않고 `validate` 단계를 반드시
  수행해야 한다.
* **FR-6.2**: 검증은 최소 다음 세 가지 레벨로 수행해야 한다.
  * **하드 제약 검증**: 명시된 아티스트 allowlist, 제외 아티스트,
    Spotify `id`/`uri` 존재 여부, 중복 트랙 여부처럼 반드시 지켜야 하는
    조건을 검사한다.
  * **커버리지 검증**: 주요 아티스트 누락, 아티스트별 최소 3곡 목표,
    후보 부족 사유 기록 여부, 전체 곡 수 또는 목표 길이 충족 여부를
    검사한다.
  * **큐레이션 품질 검증**: 단순 인기곡 나열 여부, 사용자 취향 반영,
    페스티벌/장소/상황 흐름, 곡 순서의 에너지 전개를 검사한다.
* **FR-6.3**: 하드 제약 검증 실패는 자동 수리 대상이다. 시스템은 실패한
  트랙을 제거하고, 같은 제약 안에서 후보군 재검색 또는 재선별을 시도해야
  한다.
* **FR-6.4**: 자동 수리는 제한된 횟수만 수행한다. 기본 정책은
  `generate -> validate -> repair -> validate -> final`이며, 같은 하드
  제약이 반복 실패하면 부적합 트랙을 제외한 축소 결과와 실패 사유를
  반환해야 한다.
* **FR-6.5**: 검증 결과는 내부 메타데이터로 남겨야 하며, 사용자에게 필요한
  경우 다음 정보를 설명할 수 있어야 한다.
  * 제거된 트랙 또는 아티스트와 제거 사유
  * 후보 부족으로 3곡 목표를 충족하지 못한 아티스트
  * 라인업 또는 allowlist 매칭에 실패한 항목
  * 최종 결과가 축소된 이유
* **FR-6.6**: 검증 단계는 LLM 판단만으로 끝내지 않고, 가능한 규칙 기반
  검증을 우선 적용해야 한다. 예를 들어 Spotify URI 존재, 중복 제거,
  allowlist 매칭은 deterministic rule로 처리하고, 분위기/흐름 품질은
  LLM judge 또는 휴리스틱 점수화로 보완한다.

### FR-7: 라인업 제한형 페스티벌 큐레이션

* **FR-7.1**: 사용자 프롬프트가 페스티벌, 라인업, 예습, 행사명/기간/장소,
  또는 아티스트 목록 블록을 포함하면 시스템은 `lineup-constrained`
  큐레이션 모드로 전환해야 한다.
* **FR-7.2**: `lineup-constrained` 모드에서는 프롬프트에 명시된 라인업
  아티스트 목록을 `allowedArtists`로 추출해야 하며, 이 목록은 단순 선호가
  아니라 최상위 하드 제약이다.
* **FR-7.3**: 최종 결과의 모든 트랙은 `allowedArtists` 또는
  `allowedArtistAliases`와 매칭되어야 한다. 매칭되지 않는 아티스트의
  트랙은 최종 결과에서 제외해야 한다.
* **FR-7.4**: 사용자가 입력한 취향 키워드(예: 어둡고 밀도 있는 밴드 사운드,
  몽환감, 긴장감, 기타 사운드)는 라인업 밖 유사 아티스트를 추가하는
  허가가 아니라, 라인업 안에서 후보를 점수화하고 정렬하는 기준으로만
  사용해야 한다.
* **FR-7.5**: 라인업 모드의 검색 계획은 열린 장르/감성 검색보다
  아티스트 제한 검색을 우선해야 한다. 기본 검색 단위는
  `artist:"라인업 아티스트"`이며, 표기 차이가 예상되는 경우 alias query를
  함께 시도한다.
* **FR-7.6**: Spotify Search API가 특정 라인업 아티스트의 곡을 충분히
  반환하지 못하면, 시스템은 라인업 밖 아티스트로 대체하지 않고 해당
  아티스트의 후보 부족 사유를 기록해야 한다.
* **FR-7.7**: 라인업 제한형 결과는 저장 전 검증에서 라인업 밖 아티스트
  수가 반드시 0이어야 한다. 0이 아닌 경우 최종 응답으로 간주하지 않고
  repair 단계로 되돌려야 한다.

## 3. 비기능적 요구사항 (Non-Functional Requirements)

### NFR-1: 성능 및 응답 속도 (Latency)

* **NFR-1.1**: SPEC 분해, 검색 계획 수립, Search API 병렬 조회, 아티스트
  깊이 확장, 최종 필터링 LLM 호출 등 다단계 네트워크 통신이 수반되므로,
  각 구간별 비동기 병렬 처리 및 최적화를 적용해야 한다.
* **NFR-1.2**: 2~3시간 플레이리스트를 지원하는 고도화 모드는 기존 25초
  제한보다 오래 걸릴 수 있다. MVP 기본 경로는 짧은 타임아웃을 유지하되,
  고도화 모드는 단계별 타임아웃과 후보 수 상한을 별도로 둔다.
* **NFR-1.3**: 내부 멀티턴 검색은 비용과 지연 시간을 증가시키므로,
  검색 라운드 수, 라운드별 쿼리 수, 쿼리별 `limit`, 최종 후보군 상한을
  설정값으로 제어할 수 있어야 한다.

### NFR-2: 데이터 정합성 및 안전성

* **NFR-2.1**: 최종 반환된 곡은 반드시 실존하는 스포티파이
  트랙 URI(`spotify:track:xxxx`)를 보유하고 있어야 하며, 가짜 데이터의
  유입을 원천적으로 차단해야 한다.
* **NFR-2.2**: API 응답 중 민감한 개인 세션 토큰 등은 백엔드 내부에서만
  소비되고 외부 콘솔이나 사용자 인터페이스에 노출되지 않도록 마스킹 처리한다.
* **NFR-2.3**: 외부 LLM에 전달하는 Spotify 데이터는 최종 선별에 필요한
  최소 메타데이터(곡명, 아티스트명, ID/URI, 검색 라운드 출처) 중심으로 제한한다.
* **NFR-2.4**: 검증 가능한 제약은 LLM의 자연어 판단보다 결정적 규칙을
  우선해야 한다. 특히 라인업 allowlist, Spotify URI 존재, 중복 제거,
  excluded artist 검증은 코드 레벨에서 재현 가능하게 수행해야 한다.
* **NFR-2.5**: 검증 및 repair 단계는 사용자에게 보이는 진행 상태에 포함되어야
  한다. 장시간 큐레이션에서는 "후보 검증 중", "라인업 밖 후보 제거 중",
  "부족한 아티스트 재검색 중"처럼 현재 작업을 설명해야 한다.
