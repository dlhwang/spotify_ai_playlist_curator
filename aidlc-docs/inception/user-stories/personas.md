## Persona P-001: 순간 분위기 큐레이터

### 개요

- **대표 사용자**: 특정 분위기나 상황에 맞는 playlist를 빠르게 만들고 싶은
  Spotify 사용자
- **주요 목표**: 자연어로 원하는 분위기나 상황을 설명하고, 곧바로 재생 가능한
  playlist를 얻는다.
- **동기**: 운동, 집중, 퇴근길, 파티, 휴식처럼 지금의 맥락에 맞는 음악을
  직접 고르느라 시간을 쓰고 싶지 않다.
- **기대 가치**: 사용자의 Spotify 취향과 현재 입력한 분위기를 함께 반영한
  playlist 제목, 설명, 전체 분위기 요약을 빠르게 확인한다.

### 행동 특성

- Spotify 계정이 있고 playlist 생성 기능을 자연스럽게 기대한다.
- 복잡한 설정 화면보다 짧은 자연어 입력과 명확한 결과를 선호한다.
- 추천 결과의 세부 곡 목록보다 먼저 playlist의 전체 컨셉을 확인하고 싶어 한다.
- 추천이 마음에 들면 Spotify 계정에 실제 playlist를 생성하려 한다.

### 제약과 우려

- OAuth 인증 과정이 길거나 실패하면 이탈할 수 있다.
- 추천 결과가 자신의 요청과 맞지 않으면 신뢰가 떨어진다.
- Spotify 계정에 생성되는 playlist의 제목과 설명이 어색하면 다시 사용하지
  않을 수 있다.

### 성공 기준

- 사용자가 Spotify로 인증하고 자연어 큐레이션 입력을 제출할 수 있다.
- 추천 결과에서 playlist 제목, 설명, 전체 분위기 요약을 명확히 확인한다.
- 사용자가 원하면 실제 Spotify playlist를 생성할 수 있다.
- 대표 실패 상태에서는 다음 행동을 알 수 있는 오류 메시지를 본다.

## Persona P-002: MVP 검증 개발자

### 개요

- **대표 사용자**: MVP의 기능 흐름, API 경계, 테스트 가능성을 검증하는 개발자
- **주요 목표**: Spotify OAuth, Web API adapter, LLM interface, UI 상태를
  분리된 단위로 테스트하고 빠르게 배포 가능성을 확인한다.
- **동기**: DB 없이 Vercel에서 동작하는 MVP 구조를 안정적으로 검증하고 싶다.
- **기대 가치**: 외부 API 테스트 더블과 명확한 story 검증 기준으로 구현
  범위를 관리한다.

### 행동 특성

- 실제 Spotify 연동과 테스트 더블 기반 검증을 모두 중요하게 본다.
- LLM 제공자 구현은 나중에 교체 가능해야 한다고 기대한다.
- Route Handler와 도메인 로직이 섞이지 않는 구조를 선호한다.

### 제약과 우려

- MVP에서 DB를 쓰지 않으므로 세션과 토큰 처리 경계가 모호해질 수 있다.
- 외부 API 오류 처리가 부족하면 데모 안정성이 낮아진다.
- 구현 전에 story와 acceptance criteria가 흐릿하면 테스트 범위가 흔들린다.

### 성공 기준

- 각 story가 자동화 테스트 기대값을 포함한다.
- 외부 API 경계가 테스트 더블로 대체 가능하다.
- Vercel 배포에 필요한 환경 변수와 무상태 제약이 story와 설계로 추적된다.
